---
name: weekly-context-review
description: Review visible memories, project context, and recent history; propose supported corrections and a brief for the next week. Use for requested context curation, without claiming hidden-store access.
---

Review the purpose the user names: a work project, a personal activity, or another bounded context. Use the period they specify; a Friday review can cover the past week, while a Monday preparation can check the material needed for the coming week. This skill does not schedule itself.

Inventory the surfaces actually available: visible memory entries or summaries, project instructions and files, relevant prior chats or local history, and connected-source results within the authorized scope. Record where each item was inspected. If the environment exposes none of a store, mark it unavailable. A chat response claiming to remember or forget something does not verify the stored state.

For candidate memories, separate:

- a current preference the user explicitly stated;
- a dated event or claim the user reported;
- a claim supported by an inspectable document;
- an assistant interpretation, unresolved assumption, or obsolete conclusion.

Look for broad judgments derived from temporary frustration, facts that lost their source or date, changed preferences, resolved tasks, and material from another purpose. Preserve valid inconvenient evidence. A bad afternoon does not establish a permanent character trait, and a later change of opinion does not erase what happened.

Use the format in [the review template](references/review-record.md), or produce equivalent fields in the chat. Recommend keep, correct, remove from active context, or investigate for each relevant item, with a reason and an inspectable source when available. List dependent project summaries or advice that can actually be identified. Do not invent a complete map of every derived record.

Prepare a concise next-week context brief containing checked facts, dated current preferences, open questions, and source references. Keep interpretations labeled. Treat this as a draft for the user to inspect, not a verified replacement for every provider memory store.

The default result is a review and proposed edits. Do not delete chat history, purge a local database, change memory settings, rewrite project instructions, or publish the brief without authorization for that specific action. Report proposed and completed changes separately. If the user authorizes an available edit, verify it through the exposed interface or operation result, then identify anything that remains unverified. An instruction to review memory is not permission to erase it.

The complete book resource kit also includes optional memory-correction and evidence-review skills for a specific repair or decision assessment. This skill works without them. Neither this review nor those related workflows guarantee access to all context or immunity from sycophancy.
